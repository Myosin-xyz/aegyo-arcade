The [post-login event object](https://auth0.com/docs/actions/reference/post-login/post-login-event-object) documents `event.user.last_password_reset` for database connections, absent at initial user creation. The [post-login trigger](https://auth0.com/docs/customize/actions/explore-triggers/post-login) is synchronous and explicitly includes refresh-token exchanges. A protected custom claim containing this provider state supplies a reset check on issuance/renewal that does not rely on delivery of the async password-change notification. Verify the actual top-level `prompt=none` flow independently for each client.

The final auditor refinement confirms that comparing reset claims only with an old local-session value misses a browser that keeps pre-reset Auth0 SSO but clears its app cookie. The rule therefore compares authentication itself against the reset cutoff: reject `auth_time` earlier than `last_password_reset`, regardless of local history. Every authorization request sends explicit `max_age`; normal/silent requests use a finite policy value, and required fresh login uses zero. Every adapter still validates the signed `auth_time` against its request, as required by [Auth0's reauthentication guidance](https://auth0.com/docs/authenticate/login/max-age-reauthentication).

Prefer one synchronous post-login Action to enforce the reset comparison for all three clients. The retrieved event reference describes `event.authentication.methods` but does not establish per-method timestamp fields or their equivalence to original authentication time. Prove those semantics in staging, including silent renewals; do not select an arbitrary latest MFA/custom-method timestamp. Until proven, the server-side comparison against the signed reset-state claim remains required in all three adapters, before any local session or downstream Privy authority is issued. Shared operator-cutoff checks remain in force. Timestamp precision, missing/malformed claims, explicit no-reset-yet state, and unsupported connections remain part of the proof.

The [post-login API](https://auth0.com/docs/actions/reference/post-login/post-login-api-object) supports denying the current login. Prove the selected SDK's stale-authentication error handling: clear the affected local session and retry once with `max_age=0`, remove `prompt=none`, and validate a fresh authorization transaction. Repeated or unrelated denials must produce a recoverable error without granting authority or creating a redirect loop.

This synchronous check detects changes when a token is issued or renewed; it is not an instantaneous update to all already-open apps. Choose an actual numeric local-session lifetime and prove the maximum old-session read/write window with the async Action disabled. Reconcile that bound with the existing 30-second private-state target and sensitive-write checks before declaring G1 passed; either meet the target or expose the exact deviation for a decision. Preserve active gameplay when renewal is needed. The async Action remains an acceleration path, while the shared epoch/cutoff covers operator-initiated revocation and cross-app checks.

## Second-pass agreement and final refinements

The auditor has accepted the four corrections, withdrawn Free-with-a-license-note and deferred replay as launch defaults, and corrected the event-time and environment-file findings. The following refines the first-pass table below rather than reopening the full architecture review.

### Existing-user count changes migration work, not preservation requirements

Read aggregate counts and ownership categories through authorized database/Privy access before choosing the Daebak path. **Zero existing identities needing preservation and merely a small number are different cases.** Even one existing wallet, reward recipient, or valued test/admin account needs a continuity path; test labels do not authorize deletion. Include identities that exist in Privy but have not yet created a local database row. Recheck new account creation before cutover.

If the preservation inventory confirms no legacy identities needing migration, the direct shared-provider-to-Privy JWT path may avoid a legacy linking table. It still needs custom-auth enablement, stable identity association, duplicate-provision/grant controls, recovery, and the fresh-browser proof. New member-to-Privy association remains verifiable even if it does not require another local table.

With any existing users, preserve those identities explicitly. A local dual-session link table remains a possible transitional design only with Mateo's acceptance of the actual login experience. It is not automatically selected when the September 14 checkpoint arrives. Requesting Privy enablement should be an early task for the authorized account owner after execution is approved; this audit has not submitted a provider request.

### Bulk import with a short freeze is a concrete option

The auditor's freeze proposal resolves the basic export/import race if it covers every credential/identity writer, including admin paths and in-flight requests. Define the affected endpoints, maximum window, owner, rollback trigger, and user message before choosing it. Keep ordinary browsing, existing authorized activity, and practice available. Close the provider connection to user login until the final import/reconciliation succeeds, then switch credential/recovery authority coherently.

Invalidate incompatible pre-cutover reset codes and give an affected user a clear route to request a fresh link/code from the correct provider; do not claim an obsolete code succeeded. Test a reset already in progress at the boundary. This is a small visible interruption to account writes, so it is an explicit UX tradeoff compared with first-login migration, not a zero-friction promise. If the freeze exceeds its approved bound, abort before activation or use the tested compatible recovery path.

### A small revocation design still needs freshness and delivery guarantees

Use existing local session stores and a small shared security record rather than a generalized session platform where possible. A numeric epoch alone is insufficient if a silent callback copies the latest epoch into a new local session using an old Auth0 SSO session.

Concrete failure: a browser retains SSO authentication from before a password reset; the reset increments epoch 4 to 5; the app's epoch-4 session is rejected; `prompt=none` returns a token from the old SSO session; the callback stamps epoch 5 into a fresh app session. Without checking a trustworthy original authentication time against the reset/revocation cutoff, the old session has regained authority.

Retain a reauthentication cutoff or an equivalent provider-enforced mechanism. On callback/renewal, validate supported authentication-time claims against it; do not use new token issue time as proof of user reauthentication. Validate provider revocation/token-deletion availability on the selected tier, including federated-provider behavior.

Auth0's [post-change-password Action is asynchronous](https://auth0.com/docs/customize/actions/explore-triggers/post-change-password): the password transaction does not wait for the Action to finish, and the Action's failure does not undo that transaction. Therefore test delayed, failed, duplicate, and out-of-order security notifications. Prove a supported durable detection/reconciliation path and bounded propagation behavior; do not assume one outbound HTTP request always updates Arcade. If the available mechanisms cannot enforce the agreed bound, change the recovery/security design before launch.

Global logout should also update the shared revocation state and validate provider logout, not rely only on waiting for other apps' local lifetimes. Expiry remains a fallback. Retain uncached authorization checks for sensitive actions and bounded private-view refresh/focus checks; a frequent top-level refresh must not interrupt an active game. The existing technical specification's 30-second private-state visibility target remains unless Mateo explicitly accepts another bound.

### Implementation order and readiness

- Prefer a reviewed additive Prisma migration for Aegyo's nullable unique provider mapping, consistent with its existing deployment pipeline. Preserve local sessions and role semantics.
- After the all-three shared-auth gate, make recorded-run capture plus deterministic replay the first competition implementation task. Prove all state-changing controls and timing, then build issuance/points/standings against that validated contract. No official points before verification.
- Keep the distinction between **ready to approve a plan/start a bounded staging proof** and **ready for production**. G1 and the replay proof require implementation work after approval; requiring them before any proof work would be circular. Budget, scope, and authorized access permit the bounded proof; its results permit wider implementation/cutover.

No remaining provider/user-count uncertainty is treated as user consent, a completed migration, or permission to publish the contest. These additions are included in T25–T26 of the technical specification; all end-to-end acceptance results remain pending; local component evidence is tracked separately.

## Verified provider details and implications

### Paid features must be a day-one decision

The [Auth0 pricing table](https://auth0.com/pricing), checked September 11, lists custom database connections and cross-app SSO under Professional, user import across plans, account linking from Essentials, and back-channel logout under Enterprise. The [email documentation](https://auth0.com/docs/customize/email) treats the built-in provider as a development tool and describes external SMTP/provider integration. Use the team's production email service after validating sender configuration, delivery, rate limits, and reset/verification behavior. Mailjet being present in source does not prove the SMTP integration is ready.

**Bulk import is not a route to free licensed cross-app SSO.** If the team already needs Professional for shared login, compare bulk import and first-login migration based on preservation, complexity, and actual user count rather than assuming bulk is automatically the cheaper architecture.

### Bulk password import is plausible, but requires a cutover protocol

The [import schema](https://auth0.com/docs/manage-users/user-migration/bulk-user-import-database-schema-and-examples) supports SHA-256 hashes, hex hash encoding, suffix salts, and UTF-8 or hex salt encoding. That can represent `SHA256(password + legacySecret)` in principle. The hex hash encoding does not mean the original secret is already hex-encoded. Confirm the exact production secret/history in its authorized environment and test ASCII, Unicode, and other supported password cases with synthetic data first.

Imported user IDs receive a connection-strategy prefix. Keep an explicit trusted mapping from the imported provider identity to the original local user; do not parse arbitrary subjects from another issuer/connection and assume they identify a legacy account.

The schema also states that an imported `custom_password_hash` can be updated only while the user has not logged in with the initially imported hash. Consequently, “re-import anyone who reset between export and cutover” is not a complete reconciliation strategy if provider login has already been enabled.

If bulk import is selected:

1. Inventory the actual user population and active credential/reset behavior. Preserve verification state and staff roles. Do not export event/newsletter contacts as users.
2. Install the compatible callback/local-session adapter before enabling the new public login path. Keep provider access to the imported connection closed to users during import/reconciliation; hiding a button is insufficient.
3. Import a snapshot through an authorized, secured process. Keep hashes/secrets out of logs, Git, and chat; bulk import introduces credential export that the first-login migration path avoids.
4. Reconcile all credential-affecting mutations—signup, password reset/change, deletion, identity/contact changes—using a captured revision/journal or an explicitly approved short write freeze. “Zero users” removes old-user import work, not the need to handle signups during cutover.
5. Close the final race between reconciliation and activation. Validate import job results and ID mapping, switch the login/recovery authority coherently, then enable provider login. Handle in-flight legacy reset codes without overwriting a newer provider password.
6. Test rollback with users who have already logged in or reset their password under the provider. Never restore a stale legacy password as authoritative for an activated member.

If these conditions are more work or more disruptive than a supported first-login migration, retain first-login migration. Do not impose a maintenance window or forced reset on current users without making that tradeoff explicit.

### Privy: distinguish unsupported evidence from a proven impossibility

The [Privy setup documentation](https://docs.privy.io/authentication/user-authentication/jwt-based-auth/setup) confirms access/configuration requirements and explains that a valid token holder can call Privy directly when client requests are enabled. The installed SDK exposes the browser `useLinkJwtAccount` hook. Neither observation proves the desired migration impossible; both make the feature/access and link-before-provision proof mandatory.

If the proposed September shortcut retains a separate Privy session, test this exact journey: a returning Daebak user opens a fresh browser, signs into the shared provider, opens Daebak, and tries to use the same wallet and rewards. Record every remaining email/social/wallet prompt. One-time proof to associate an old account is different from a recurring second account login. Mateo must accept that transition explicitly if full shared login cannot be delivered.

Do not remove existing Google/Apple or external-wallet recovery paths merely because the central login starts with email/password. The original seamless-current-user requirement still applies.

1. One correctly licensed managed auth provider, with one client per product.
2. Aegyo exchanges verified provider authentication for its existing local session and preserves content/roles.
3. Arcade hosts a small account/profile module and member/username tables alongside its new competition tables. Start with account screens under Arcade's existing origin; defer a new account hostname and standalone deployment.

5. Existing sessions and known mappings avoid unnecessary new profile-service calls on public browsing or ordinary wallet recovery. New linking and sensitive identity changes fail safely if the directory is unavailable.
6. Preserve retry-safe link state and sufficient security/revocation state. A separate package, generalized event bus, and unused chat endpoints can wait. Simplify infrastructure without deleting correctness requirements.
7. Daebak's final auth behavior is determined by the verified Privy proof or an explicitly accepted transition. A local link table alone does not settle it.
8. Capture and replay official game inputs as one feature. Keep pending evidence out of official points until verified. If necessary, propose one verified initial game instead of two; obtain agreement before advertising or enrollment.

This reduces infrastructure work without treating an unverified provider integration as working or weakening official scores. The delivery plan and technical specification now replace the standalone Accounts app/separate database with this lean module. Audit approval covers proof structure; no implementation or paid provisioning is represented as complete.
